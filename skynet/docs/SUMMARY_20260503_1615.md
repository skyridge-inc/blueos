## Why "lay the rover flat" wasn't enough

The user laid the rover flat between runs, but "flat" in the user's
visual frame doesn't necessarily equal "Pixhawk body Z = down." The
Pixhawk could be:

1. Mounted in the rover at a 90° rotation that `AHRS_ORIENTATION=35`
   compensates for *only when the rover is in driving orientation*, OR
2. Removed from the rover and placed loose on the bench in an
   arbitrary orientation, OR
3. In a rover that's parked sideways (on its side, not wheels-down).

Without seeing the physical setup we can't tell which. But the data
unambiguously says the autopilot reads gravity perpendicular to where
it expects.

In the field this doesn't matter: GSF/EKF re-aligns yaw against
GPS-derived velocity, and the EKF refines roll/pitch toward 0. On a
stationary bench with HIL `vn=ve=0` injection, there's no velocity
input for GSF to align against, so the EKF locks to its
tilt-alignment-time estimate and stays there.

## Fix Implemented

Rather than retry "lay it flatter, try again," add a **pre-arm
orientation gate** that fails the sim with a clear error before it
spends 15 s reproducing the freeze.

### What changed

- **`gps_sim.py`** — `request_diagnostic_streams` now subscribes to
  `ATTITUDE` at 1 Hz. The gate needs fresh roll/pitch to read.
- **`cli.py`** — added `last_attitude_roll_rad`, `last_attitude_pitch_rad`,
  and `orientation_check_failed` state. New `ATTITUDE` handler stashes
  the latest values. New gate runs on every healthy tick before the
  auto-arm block. If `|Roll|` or `|Pitch|` exceeds `ORIENTATION_LIMIT_DEG=15`,
  the gate prints:

  ```
  Pre-arm orientation check failed: Roll=+90.8° Pitch=+3.5° (limit ±15°).
  The autopilot thinks the vehicle is on its side. AR_PosControl will
  produce zero desired_speed in this state and AUTO will freeze. Sit the
  rover/Pixhawk in its normal driving orientation (gravity along body Z
  axis) and re-run.
  ```

  ...and trips the watcher with reason `pre_arm_orientation_failed`.
  The auto-arm block now also gates on `not orientation_check_failed`,
  so the arm command never goes out.

- **`tests/test_gps_sim.py`** — extended `TestStreamRequests` to expect
  the `ATTITUDE` subscription. **301 tests pass.**

### Why a 15° limit

Real rovers traverse slopes; 5° was tempting but would false-positive
on a hill. 15° gives margin for any field condition while still
catching the failure mode (which is at ±90°, not subtle). If a future
mission deck genuinely needs >15° static tilt the constant is one line.

### Why pre-arm rather than continue

Two reasons:

1. **Fast feedback.** The user gets a clear actionable error in <2 s
   instead of waiting 15 s for the auto-fail trigger.
2. **No false forensic logs.** Before this change, every "rover is on
   its side" run captured a 3 MB dataflash log to `logs/`. After the
   gate, those logs are only captured for *real* freezes (not
   user-error setups) — preserves the signal-to-noise of the captured
   evidence.

## Root cause of the orientation: AHRS_ORIENTATION=35 mismatch

`AHRS_ORIENTATION=35` is `ROTATION_ROLL_270_PITCH_270`. Working out
its rotation matrix for sensor → body:

- Roll 270° around X: `(Xs, Ys, Zs)` → `(Xs, Zs, -Ys)`
- Pitch 270° around the result: `(Xs, Zs, -Ys)` → `(Ys, Zs, Xs)`

So with `AHRS_ORIENTATION=35`:
- `body X = sensor Y`
- `body Y = sensor Z`
- `body Z = sensor X`

A flat Pixhawk (board face up) reads `sensor Z ≈ -9.81`, sensor X/Y
≈ 0. After the rotation, gravity lands on **body Y**, not body Z —
exactly what we see (`AccY ≈ -9.78`). The setting is correct *only
if the Pixhawk is mounted with its `+X` axis pointing down*, an
unusual orientation.

The user's intent is "flat with `+X` arrow forward, board face up,"
which matches `AHRS_ORIENTATION=0` (`ROTATION_NONE`).

## Fix applied to the live autopilot

```
PARAM_SET AHRS_ORIENTATION = 0.0  (was 35.0)
PREFLIGHT_REBOOT_SHUTDOWN
```

Verification after reboot:

| Reading | Pre-fix | Post-fix |
|---|---|---|
| Raw IMU0 `AccX` | +0.59 | +0.14 |
| Raw IMU0 `AccY` | -9.78 | +0.59 |
| Raw IMU0 `AccZ` | +0.14 | **-9.77** |
| EKF Roll | +90.8° | **-3.47°** |
| EKF Pitch | +3.5° | +0.80° |

Pixhawk is now level relative to body frame. EKF roll/pitch are well
within the 15° pre-arm gate's threshold.

**Caveat:** if the Pixhawk gets re-mounted in the rover with a
different physical orientation, `AHRS_ORIENTATION` will need to be
re-set. The "correct" value depends on the actual mount, not on a
universal answer. A re-mount + accel calibration via QGC is the
robust path; ad-hoc orientation guesses won't hold up to roll/pitch
during real driving.

### Pivot-vs-non-pivot ruled out

Hypothesis tested: maybe pivot is active (since yaw_error = 90°
exceeds `WP_PIVOT_ANGLE=60`) and `_pivot.get_turn_rate_rads` returns
0 for some reason.

Set `WP_PIVOT_ANGLE=0` to disable pivot entirely. Re-ran sim
(log21). **Same freeze.** So the freeze is in the non-pivot path
through `AR_PosControl`, not the pivot path.

After confirming, restored `WP_PIVOT_ANGLE=60` to the autopilot.

### Where the zero comes from

In `AR_WPNav::update`:

1. Guard clause has 4 conditions; we've ruled out 3 of 4 (armed ✓,
   `_orig_and_dest_valid` ✓, `ahrs.get_location` ✓). The 4th —
   `_atc.get_forward_speed(speed)` — succeeds with `speed=0` for
   EKF3 with healthy velocity (which we have, just zero magnitude).
2. `update_distance_and_bearing_to_destination()` runs (we see
   WpDist=10).
3. With pivot disabled, `advance_wp_target_along_track()` should
   run. It calls `_pos_control.set_pos_vel_accel_target(target_pos,
   target_vel, target_accel)`.
4. `_pos_control.update(dt)` then runs and produces
   `_desired_speed`, `_desired_turn_rate_rads`, `_desired_lat_accel`.

For all three to be 0, either (a) `_pos_target_valid` stays false
because `advance_wp_target_along_track` early-returned, OR (b)
target_pos == current_pos so `_p_pos.update_all` returns zero
velocity command, OR (c) the SCurve produced no path.

`advance_wp_target_along_track` has its own guard clause:
```cpp
if (!AP::ahrs().get_relative_position_NE_origin(curr_pos_NE) ||
    !AP::ahrs().get_velocity_NED(curr_vel_NED)) {
    return;
}
Vector2f origin_NE;
if (!_origin.get_vector_xy_from_origin_NE(origin_NE)) {
    return;
}
```

Most likely suspect: `_origin.get_vector_xy_from_origin_NE` failing
because the EKF origin returned by `AHRS::get_origin` doesn't match
the origin AR_WPNav captured from `set_desired_location`'s
stopping-point computation. Or the SCurve isn't initialized with
non-zero limits.

## Suggested Next Step

The remaining mystery is upstream of `AR_PosControl::update` —
something is preventing `_vel_target` from being non-zero even
though the autopilot has a valid waypoint, valid origin, and valid
EKF state.

Two concrete next experiments, in order of cheapness:

1. **GUIDED mode test.** Send `SET_POSITION_TARGET_GLOBAL_INT` with a
   real target while the autopilot is armed and in GUIDED mode.
   GUIDED uses `Mode::set_desired_location` too, but a different
   submode dispatch and (in some paths) different SCurve init.
   If GUIDED produces motion and AUTO doesn't, the bug is in
   `ModeAuto`'s submode handling or mission dispatcher; if both
   freeze, the bug is in shared `AR_WPNav`/`AR_PosControl` code.

2. **Add a per-tick MAVLink debug stream** that exposes
   `_pos_target_valid`, `_vel_target.x/y`, `_pos_target.x/y`, and
   `_p_pos.get_pos_error()` from `AR_PosControl`. ArduPilot exposes
   this via `MAV_CMD_DO_SEND_BANNER` or by writing a tiny custom
   GCS_MAVLink message hook. This requires a custom firmware build
   on the Pi, but tells us *exactly* which of the three failure
   modes (a/b/c above) is firing.

Path 1 is faster; path 2 is more diagnostic. If path 1 reveals
GUIDED works, the bug is constrained enough that we can probably
patch it without path 2.
