### 1. Replaced dead GUIDED-fallback intent with auto-download trigger

**New file:** `src/skynet/log_download.py` (~210 lines).

Implements the legacy DataFlash-Over-MAVLink download protocol:
`LOG_REQUEST_LIST` → collect `LOG_ENTRY` messages → `LOG_REQUEST_DATA`
chunks → reassemble in offset order → write `.bin`. Includes
offset-based gap retry, per-offset retry cap, and skip of zero-size
active logs (the "must disarm first to seal" semantics).

**New tests:** `tests/test_log_download.py` (13 tests, all green;
suite total = 301 passed).

**Wiring in `cli.py`:** the existing `auto_engaged_at` and
`ever_saw_throttle` variables now drive a real trigger:

```python
if (
    nav_engaged
    and drive_mode_normalised == "auto"
    and auto_engaged_at is not None
    and not ever_saw_throttle
    and not auto_fail_log_grab_pending
    and (_time.monotonic() - auto_engaged_at) > AUTO_FAIL_LOG_GRAB_S
):
    auto_fail_log_grab_pending = True
    watcher.trip("auto_throttle_fail")
```

Post-loop helper `_grab_dataflash_after_auto_fail` disarms the autopilot
(seals the active log), drains stale traffic, and downloads the latest
log to `./logs/sim_dataflash_<ts>_log<id>.bin`.

### 4. SITL HIL run — different failure mode again

Re-ran `skynet nav sim` against the Pi's SITL via `tcp:sky1:5810` to
test whether HIL `GPS_INPUT` injection alone reproduces the V13 freeze.

Two infrastructure fixes were needed first:
- `REBOOT_WAIT` 8 → 12 s. Real Pixhawk reboots in ~6–8 s; SITL's

### 6. Forensic analysis of `log15`

Timeline reconstructed from `MODE`, `ARM`, `EV`, `MSG` rows:

| TimeUS | Event |

Inside the freeze window:

| Source | Value | Meaning |
|---|---|---|
| `XKF1.Roll` (all 3 cores) | **+82.46°** | EKF says vehicle is on its side |
| `XKF1.Pitch` | -5.41° | |
| `XKF1.Yaw` | 105.15° | matches our HIL injection |
| `XKF1.VN, VE, VD` | ~0 (~1e-3) | matches our `vn=ve=0` injection |
| `THR.DesSpeed` | **0.0** | throttle controller asked for zero speed |
| `STER.DesTurnRate` | **0.0** | steering controller asked for zero turn |
| `STER.DesLatAcc` | 0.0 | |
| `RCOU.C1, C3` | 1500 µs | servos confirmed neutral |

The `WpDist=9.99 m` and `WpBrg=15.17°` populated correctly at the AUTO
mode change at t=38.5 s — set by `AR_WPNav::set_desired_location()`.
But `_desired_speed_limited` and `_desired_turn_rate_rads` stay zero
forever, which means **`AR_WPNav::update()` is firing the guard-clause
early return on every tick** (`AR_WPNav.cpp:146`).

Of the four guard conditions, three are clearly true (armed,
`_orig_and_dest_valid`, `AHRS::get_location` succeeds — flags=831).
The remaining one (`_atc.get_forward_speed`) returns true with
`speed=velocity.x*cos_yaw + velocity.y*sin_yaw ≈ 0`, which *should*
let the guard pass.

**Hypothesis:** the guard does pass, but downstream
`AR_PosControl::update(dt)` projects desired NE motion through an
82°-rotated body frame and the forward-component projection collapses
to ~0, producing `_desired_speed_limited = 0` and a near-zero turn rate.

### 7. Confirmed the root cause via raw IMU vs EKF comparison

```
Raw IMU0 accel (last 50 samples avg):
  AccX=-0.92  AccY=-9.69  AccZ=-1.28 m/s²   |g|=9.82 m/s²
Implied tilt from accel: Roll=-97.52°  Pitch=+5.40°
EKF reports:              Roll=+82.46°  Pitch=-5.41°
```

`|g| = 9.82 m/s²` is exactly Earth gravity → IMU calibration is healthy.
The gravity vector points along **body Y axis** rather than body Z axis.
After `AHRS_ORIENTATION=35` (`ROTATION_ROLL_270_PITCH_270`) is applied,
EKF computes the consistent attitude — Roll=+82.46°.

**Conclusion: the Pixhawk is physically not level on the bench.**

`AHRS_ORIENTATION=35` is correct for the rover's *driving* mounting.
The bench position is rotated ~90° further from that. In the field,
GSF/EKF re-aligns yaw against real GPS-derived motion, the Roll/Pitch
estimate corrects, and `AR_PosControl` runs normally. On the bench
with HIL `vn=ve=0` injection, there's nothing for GSF to align against,
and the EKF stays locked to its tilt-alignment-time estimate forever.

V13's "ArduRover firmware bug" was a methodology failure: every round
of investigation added MAVLink telemetry but never changed evidence
*layer*. One round of dataflash inspection answered what 13 rounds of
MAVLink couldn't.
