## Fixes Implemented (This Session)

Cumulative chain of fixes built up across this multi-hour session.
Each had an observable failure mode that pointed to the next.

### Fix 1 — Restored `--rotation-speed` and `--manual-settle-time` switches (twice)

Both switches existed at session start as uncommitted work, then
silently disappeared from the working tree between turns (cause never
identified — possibly an IDE auto-revert, possibly a `git checkout`
in another shell). Re-added with new defaults and pinned via tests.

- **`--rotation-speed`** caps `SkidSteerModel`'s kinematic pivot rate
  in deg/s. Replaces the prior hardcoded 60°/s. Default 6°/s.
- **`--manual-settle-time`** holds the rover stationary for N seconds
  after motor test, while GPS_INPUT and VISION_POSITION_ESTIMATE keep
  flowing, before AUTO engages. Default 30 s.

### Fix 2 — Spawn heading aligned to WP1 (was 90° CW)

Through V10–V13 the spawn heading deliberately faced 90° away from
WP1, exercising the nav controller's pivot+throttle paths. With the
V13 freeze fixed, that 90° offset became a *liability*: AUTO entered
with a 90° yaw error, which on a stationary HIL Pixhawk the EKF
couldn't track via vision yaw (the deeper Fix 5 issue). Realigning
spawn → WP1 means AUTO has only forward translation to do at the
start, which the EKF already tracks fine via GPS velocity.

### Fix 3 — Settle uses HOLD instead of MANUAL

The user's request was MANUAL settle, but the live behavior on this
rover proved MANUAL is fundamentally fragile: ArduRover's MANUAL is
RC-passthrough, and a real RC source on the rover (transmitter or
stuck SBUS receiver) was providing full-throttle input. Our
RC override at 1500/1500 lost the race against the real RC under
NetBird congestion (50% packet loss at 7.2 Hz vs target 15 Hz). HOLD
ignores RC entirely; the EKF gets the same sensor data (GPS_INPUT,
VPE) for settling but the rover stays still regardless of RC state.

### Fix 4 — Spelling: `EK3_GYR_P_NSE` → `EK3_GYRO_P_NSE`

A previous turn lowered `VISO_YAW_M_NSE` and added an
`EK3_GYR_P_NSE` override to make the EKF track vision yaw faster.
The yaw-noise change took, but `EK3_GYR_P_NSE` was rejected silently
by the autopilot — the actual ArduRover 4.6.3 param name is
`EK3_GYRO_P_NSE` (with the **O**). ArduPilot drops unknown
`PARAM_SET` messages without ack, and our `Sim param ... not found
on autopilot` warning scrolled past in 6 s of startup output.

Negative-assertion test added: `assert "EK3_GYR_P_NSE" not in
SIM_PARAMS` — pins the correct spelling so a future maintainer can't
silently reintroduce the typo.

### Fix 5 — Disabled compass yaw fusion (the killer)

After Fix 4 landed correctly, EKF tracking improved from 0.2°/s to
~2.2°/s during pivots — still ~38% of the predicted 92% gain. The
forensic clue was `compass_var` growing from 0.38 to 7+ during the
WP3 turn: **the EKF was still fusing compass innovations even though
`EK3_SRC1_YAW=6` selects ExternalNav as the primary yaw source.**
Compass fusion in ArduPilot's EKF is independently controlled by
`COMPASS_USE / USE2 / USE3`. With those at the rover's default, the
EKF was being pulled between a steady physical compass and a rotating
vision yaw, and the residuals couldn't relax.

Setting `COMPASS_USE = COMPASS_USE2 = COMPASS_USE3 = 0` removed the
second yaw source. Today's run shows `compass_var` ≤ 0.11 throughout,
and the EKF tracks vision yaw within a few degrees of the kinematic.

This was also the most likely cause of the `Critical: EKF variance`
trip seen in the prior session at 14:45:46 — two contradictory yaw
sources that the EKF can't reconcile produce growing variance until
some hard threshold is crossed.

### Fix 6 — Added `EK3_GYRO_P_NSE` to the late-writes whitelist

Defense in depth. The post-reboot late-write pass (originally added
in V4 for `VISO_*` params that materialize only after `VISO_TYPE=1`
is persisted across a reboot) now also includes `EK3_GYRO_P_NSE`,
so a missed initial fetch can't silently leave the EKF on default
gyro tuning.
