### 3. Wired the `nav-plan` Typer command into `cli.py`

Added a single new command after `upload`:

```python
@app.command("nav-plan")
def nav_plan(
    kml_file: Path,
    width: float,                    # --width / -w  in inches  (required)
    output: Optional[Path] = None,   # --output / -o
    visualize: bool = False,         # --visualize
    kml_track: bool = False,         # --kml-track
    kml_tour: bool = False,          # --kml-tour
) -> None: ...
```

Behavior matches the `provisioning-cli` `Requirement: nav-plan Command`
exactly:

- Parses the KML polygon, projects to local XY meters, extracts the spine,
  and runs `generate_contour_paths`.
- Writes `<base>.waypoints` for a single-mower result, or
  `<base>_mower1.waypoints` … `<base>_mowerN.waypoints` for multi-mower.
- Strips any extension from `--output` so `-o /tmp/mission.waypoints` and
  `-o /tmp/mission` produce the same output base.
- Honors `--visualize`, `--kml-track`, and `--kml-tour` independently — any
  combination produces the corresponding `<base>.html`, `<base>_track.kml`,
  and `<base>_tour.kml` files alongside the `.waypoints` files.
- Prints, in order: polygon vertex count, spine vertex count, mower width
  (inches and meters), mower count, output paths, and any visualization
  paths.
- Imports from `.mission_planning` are done **inside the function body** so
  that `shapely` is not loaded for unrelated commands like `connect` or
  `read` — keeps cold-start cost off the MAVLink path.
- Opens **no** MAVLink and **no** HTTP connection. Pure file-to-file.

Verified registration with `uv run skynet nav-plan --help`.

## Decisions & Trade-offs

### Subpackage rather than top-level modules

`mission_planning` lives at `src/mower_provisioner/mission_planning/` rather
than as five sibling files next to `cli.py`. Reasons:

- Namespacing: keeps the five new modules from cluttering the root package
  alongside existing `params.py`, `config.py`, `connection.py`, etc.
- Optional imports: heavy imports (`shapely`, `numpy`) are confined behind
  the subpackage, so MAVLink-only commands like `connect` and `read` don't
  pay for them on cold start. Combined with the function-local import inside
  the `nav_plan` Typer command, this means `skynet --help` and `skynet read`
  do not import `shapely`.

### Verbatim copy rather than refactor

The five source files were copied unchanged from `nav_planning`. This was
deliberate:

- The spec was deliberately written to match the existing observable
  behavior of `nav_planning`, so any "improvements" risked introducing spec
  drift.
- Refactoring could be done in a follow-up after the original `nav_planning`
  project is decommissioned — that's a separate concern from "make the spec
  satisfied."

### Dropped one CLI test

`test_polygon_too_narrow_exits_nonzero` was written to cover the
`num_mowers == 0 → exit 1` branch in `cli.py`, but it turned out that branch
is essentially unreachable from real KML input: `extract_spine` always
returns ≥ 2 points, the spine always starts at a polygon vertex, and
`polygon.intersection(spine_line)` is therefore always non-empty — so the
spine itself is always added as path 1 and `num_mowers >= 1`. The defensive
guard in `cli.py` is cheap and was kept (it costs nothing if it's never
triggered), but its test was removed rather than synthesizing a degenerate
shapely geometry to force the branch.

## Outstanding / Follow-ups

- **Decommission `../nav_planning`.** The standalone `nav_planning` project
  is now functionally duplicated inside `skynet`. A follow-up should remove
  it or replace its CLI entry point with a thin shim that calls
  `mower-provisioner nav-plan`, then update any documentation that points at
  the standalone CLI.
- **`skynet` console script naming.** `pyproject.toml` registers the entry
  point as `skynet`, but the existing `provisioning-cli` spec language
  (carried over from earlier work) refers to `mower-provision`. The new
  `nav-plan` requirement uses `mower-provision` in its scenarios for
  consistency with sibling requirements; if the canonical name is
  `skynet`, both should be normalized in a separate cleanup pass.
- **Spec drift on the unreachable error branch.** The `mission-planning`
  spec includes a "polygon too narrow → non-zero exit" scenario that
  describes the defensive guard in `cli.py`. The guard exists, but it cannot
  currently be triggered from any real KML polygon. If the contour
  generation algorithm is later changed in a way that *can* produce zero
  paths, that scenario will become testable; for now it documents intended
  behavior more than verified behavior.
