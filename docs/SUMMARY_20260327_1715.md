# BlueOS Configuration Audit — sky1 (192.168.1.117)

**Date:** 2026-03-27 17:15
**Target:** Raspberry Pi 5, BlueOS 1.5.0-beta.32 (arm64)
**Autopilot:** CubeOrange+ via `/dev/ttyACM0` at 115200 baud
**Firmware:** ArduPilot Rover 4.6.2 STABLE
**Hostname:** sky1

---

## Executive Summary

QGroundControl could not connect because no MAVLink UDP client endpoint targeted the 192.168.1.x subnet. **Resolved** by removing stale push endpoints and switching to a QGC-initiated UDP model — QGC connects to each vehicle's `udpin:0.0.0.0:14550` on demand, which is better suited for fleet switching over the NetBird VPN overlay. Additionally, the autopilot is reporting **MAV_STATE_CRITICAL**, the camera manager has **zero video streams configured**, and MediaMTX is being probed with invalid URLs every 6 seconds.

---

## 1. MAVLink Telemetry — RESOLVED

### Original Problem

Two stale push (`udpout`) endpoints were configured, neither reaching the GCS:

- `udpc:192.168.2.1:14550` — wrong subnet (192.168.2.x, not 192.168.1.x)
- No endpoint targeting the actual GCS subnet

### Fix Applied

Removed both outbound push endpoints and switched to a **QGC-initiated UDP model**:

1. **Removed** `GCS Client Link` (udpout to 192.168.2.1:14550) — stale, wrong subnet
2. **Removed** `QGC LAN` (udpout to 192.168.1.109:14550) — interim fix, superseded

The existing `GCS Server Link` (`udpin:0.0.0.0:14550`) remains. This endpoint listens for incoming UDP packets from any GCS. When QGC sends to `vehicle_ip:14550`, MAVLink-Server detects the source address and routes telemetry back automatically.

Vehicles are connected via NetBird VPN overlay. In QGC, create UDP links per vehicle (**Application Settings > Comm Links > Add**):

| Name | Type | Server Address | Port |
|---|---|---|---|
| sky1 | UDP | 192.168.1.117 | 14550 |
| sky2 | UDP | (sky2 IP) | 14550 |
| sky3 | UDP | (sky3 IP) | 14550 |

Connect/disconnect each link on demand to switch between vehicles.

### Autopilot State: CRITICAL

The HEARTBEAT message reports:

```
type: MAV_TYPE_GROUND_ROVER
autopilot: MAV_AUTOPILOT_ARDUPILOTMEGA
system_status: MAV_STATE_CRITICAL
custom_mode: 4 (HOLD)
```

`MAV_STATE_CRITICAL` typically indicates a pre-arm failure or sensor error (e.g., GPS, compass, accelerometer). This is separate from the connectivity issue but warrants investigation once QGC is connected.

### Serial Port Boot Delay

At system boot (02:00 UTC), the MAVLink-Server failed to open `/dev/ttyACM0` for approximately **9 minutes** (02:00:00 to 02:09:23) with repeated `No such file or directory` errors at 1-second intervals. The CubeOrange+ USB device eventually enumerated, and the connection succeeded. This is likely a race condition between BlueOS container startup and USB device initialization on the Pi 5.

## 2. Video Streaming — NOT FUNCTIONAL

### Camera Manager

- **Process:** `mavlink-camera-manager --default-settings BlueROVUDP`
- **Configured streams:** `[]` (empty — zero streams)
- **MAVLink connection:** `tcpout:127.0.0.1:5777` (internal to MAVLink-Server)
- **Default settings:** `BlueROVUDP` — this is the **marine/ROV default**, not appropriate for a ground rover. No harm currently since no streams are configured, but the default video endpoints would target wrong ports if auto-configured.

### V4L2 Devices

20 video devices detected (`/dev/video19` through `/dev/video37`), which is typical for a Pi 5 with ISI/Unicam subsystem. However, none are configured as streams in the camera manager.

### MediaMTX Extension (v1.11.4)

**Container:** `extension-williangalvaniblueosextensionmediamtxv1114` (host networking)

**Configuration** (`/usr/blueos/extensions/mediamtx/mediamtx.yml`):

```yaml
rtspAddress: :8555
paths:
  front:
    source: rtsp://192.168.1.10:5005/routecam
    sourceProtocol: udp
    sourceOnDemand: no
```

- RTSP relay is configured to proxy the RouteCAM at `192.168.1.10:5005/routecam` as the `front` stream on port 8555.
- **Stream URL:** `rtsp://192.168.1.117:8555/front`

### MediaMTX Errors

The logs show a **continuous 6-second polling loop** hitting MediaMTX with invalid requests:

```
[RTSP] [conn 127.0.0.1:xxxxx] closed: invalid URL (/)
[RTMP] [conn 127.0.0.1:xxxxx] closed: invalid rtmp version (71)
```

This is the BlueOS camera manager or nginx health-check probing MediaMTX with root-path requests. Not causing failures, but generating constant log noise.

### MediaMTX API Port

Port 9997 (the default MediaMTX API port) is **not listening**. The configuration may have the API disabled, or the extension uses a non-standard API port. Unable to verify active stream status via API.

## 5. Recommended Actions

### ~~Priority 1: Fix QGC MAVLink Connectivity~~ RESOLVED

Switched to QGC-initiated UDP model. Removed stale push endpoints. QGC connects to vehicle's `udpin:0.0.0.0:14550` on demand — no vehicle-side changes needed when switching between mowers. Configure UDP links in QGC per vehicle (see Section 1).

### Priority 2: Investigate MAV_STATE_CRITICAL

Once QGC connects, check:
- Pre-arm messages (Messages tab)
- Sensor health (compass, GPS, accelerometer calibration)
- The vehicle is in HOLD mode (custom_mode=4) which is expected when critical

### Priority 3: Configure Video Streams

- The camera manager has zero streams. If you want to use the built-in camera manager for Pi cameras, configure a stream via the BlueOS Video page.
- The MediaMTX extension is already proxying the RouteCAM. To view in QGC, you may need to manually add `rtsp://192.168.1.117:8555/front` as a video source.
- Consider whether both the camera manager and MediaMTX extension are needed, or if one can handle all video.

### Priority 4: Reduce Log Noise

The BlueOS health-check is polling MediaMTX every 6 seconds with invalid URLs. This is cosmetic but clutters logs. The MediaMTX extension configuration could expose a health endpoint, or the polling could be adjusted.
